What Is Vibe Coding?

The mindset shift, the four-step loop underneath it, and a map of where it belongs versus where it will quietly hurt you.

Overview & Objectives

"Vibe coding" is what people started calling it when you build software mostly by describing what you want to an AI model and steering its output, rather than typing every line yourself. It's not a new programming language or a new tool category — it's a different division of labor between you and the machine, and this module is about understanding that division clearly enough to use it on purpose.

By the end of this module, you'll be able to:

  • Define "vibe coding" and describe how it differs from traditional hand-written coding
  • Walk through the four-step loop — prompt, generate, read, judge/iterate — that sits under every vibe coding session
  • Sort a task as a good fit for vibe coding, or one that needs more rigor, and explain why
  • Explain the core risk: fluent-sounding output is not the same thing as correct output

Prerequisites: none. This module assumes no prior coding experience.

Content Modules

s1 — Where the term comes from, and what it actually means

The phrase entered common use in 2025 to describe a specific experience: you describe a feature or a fix in plain language, the AI writes the code, and you evaluate the result "by vibe" — does it look right, does it run, does it do the thing — rather than reading every generated line the way you'd review a colleague's pull request.

That's a real and useful mode. It's also easy to misapply. The name describes a feeling (fast, conversational, low-friction), not a guarantee (correct, secure, maintainable). Everything else in this workshop is about keeping the feeling while not losing the guarantee where it matters.

Analogy

It's closer to briefing a capable contractor than to typing. You describe the outcome, they do the work, and your job shifts from "produce every detail" to "specify clearly, inspect what comes back, and know when to ask for changes."

s2 — The loop underneath every session

Whether you notice it or not, every vibe coding session runs the same four-step loop. Naming the steps makes it possible to debug a session that's going badly — you can usually tell which step just failed.

1 · Prompt

You describe the goal, the constraints, and what "done" looks like.

2 · Generate

The AI produces code, an explanation, or both — in seconds, not minutes.

3 · Read

You actually look at what came back, not just whether it ran.

4 · Judge / Iterate

Accept it, reject it, or send back a specific correction. Repeat.

Module 2 goes deep on steps 1, 3, and 4 — writing prompts that hold up, reading output like a reviewer instead of a spectator, and iterating without starting over each time.

s3 — Where it shines, where it's risky

The loop works the same everywhere, but the stakes of a bad step 4 don't. Use this as a rough sorting rule, not a hard boundary — Module 3 covers the judgment calls in between.

Good fit for vibe codingNeeds more rigor
Throwaway scripts, one-off data cleanupsAnything touching money, health, or legal data
Prototypes you'll validate then rebuildCode that ships straight to production users
Boilerplate and glue code you can read at a glanceSecurity-sensitive logic (auth, permissions, payments)
Exploring an idea before you've committed to itAnything you can't easily test or verify
The core risk

AI output is fluent by default — confident-sounding code and confident-sounding explanations come at the same price. Fluency is not correctness. A hallucinated function call and a real one read identically until you check.

Activity — Sort the Scenario

Type: Sorting · Time: 10 min, individual then pair-share

For each scenario below, decide: is this a good fit for vibe coding, or does it need more rigor (careful review, tests, or a second pair of eyes before it ships)? Pick an answer for each, then check your mapping.

A one-time script to rename 200 files by a pattern.
Right — low stakes, easy to eyeball the result before you run it.
Reconsider — what's the actual cost if this renames the wrong files?
A function that calculates a customer's refund amount.
Right — money math needs tests and a human check, not just a glance.
Reconsider — this touches money. A silent off-by-one here costs someone real dollars.
A quick prototype landing page to show a stakeholder tomorrow.
Right — it's disposable and you'll rebuild it properly if the idea sticks.
Reconsider — nothing here ships to real users or handles real data yet.
Code that checks whether a logged-in user is allowed to view a page.
Right — access control is security-sensitive. Get a second pair of eyes.
Reconsider — this is exactly the kind of logic where a subtle bug becomes a data leak.
