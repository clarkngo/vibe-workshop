The Vibe Coding Loop: Prompt, Review, Iterate

The three skills that separate a productive vibe coding session from a frustrating one: prompting with enough detail, reading output like a reviewer, and iterating without starting over.

Duration: 60 min Difficulty: Introductory Strand: Practice
1Overview 2Content 3Activity 4Simulation 5Review 6Further Reading
1

Overview & Objectives

Module 1 named the loop: prompt, generate, read, judge/iterate. This module is where you actually get good at three of those four steps — the ones that are a skill, not just a click.

By the end of this module, you'll be able to:

  • Write a prompt that includes context, constraints, and a clear definition of "done"
  • Skim AI output the way a reviewer would: what changed, does it match intent, any red flags
  • Iterate with a specific follow-up instead of discarding the result and starting over
  • Know when to paste an error message back verbatim versus re-explaining the goal

Content Modules

s1 — Anatomy of a prompt that holds up

A prompt that gets you a usable result on the first or second try tends to have four ingredients. You don't need all four every time — a throwaway script needs less than a customer-facing feature — but when a prompt fails, it's almost always missing one of these.

Context

What already exists. "Here's my current function" beats "write a function."

Constraints

The boundaries. Language, library, performance, style — say what's fixed.

Example

A concrete input/output pair removes more ambiguity than another paragraph of description.

Success criteria

How you'll know it's done: "the page loads," "the test passes," "handles an empty list."

Before / after

Before: "Add a login form." After: "Add a login form to this page (context: existing HTML pasted below) with email + password fields (constraint), matching the input style already used on the signup form (example), that shows an inline error on a failed login instead of a blank screen (success criteria)."

s2 — Reading output like a reviewer, not a spectator

The habit that separates people who get good results from people who get burned isn't a better prompt — it's what they do in the ten seconds after the output appears. Ask three questions before you accept anything:

  1. What actually changed? Skim the diff, not the AI's summary of the diff. The summary can be wrong or incomplete.
  2. Does it match what I asked for? Not "does it look plausible" — does it satisfy the success criteria you set in s1.
  3. Any red flags? A function you don't recognize, an import that seems unrelated, an error being silently swallowed, a change to a file you didn't mention.

This takes seconds once it's a habit. It's the single highest-leverage thing in this whole module.

s3 — Iterating without starting over

Most first outputs are close but not quite right. The instinct to throw it away and re-explain from scratch wastes the part that was already working. Reach for one of these instead:

PatternWhen to use it
Narrow the askThe shape is right but one part is wrong — say exactly which part, leave the rest alone.
Paste the error back verbatimSomething broke and you have an actual error message — paste it exactly, don't paraphrase it.
Ask for the reasoningThe output looks odd but doesn't obviously fail — ask "why did you do it this way" before you decide.
Ask for testsYou're not sure the logic is right — ask for test cases, including edge cases, before you trust it.
Watch for

Scope creep: three iterations in, check whether you're still solving the original problem or a bigger one you backed into. If it's bigger, that's fine — just say so out loud and reset expectations.

Activity — What's Missing?

Type: Matching · Time: 12 min, individual then pair-share

Each prompt below is missing exactly one of the four ingredients from s1. Identify which one, then check your answers.

"Write a function that sorts a list of customer records."
Right — sort by what field? Ascending or descending? That's a constraint.
Reconsider — what's fixed here that the AI has to guess at?
"Reformat this CSV data to match our standard layout." (no sample of "our standard layout" attached)
Right — "our standard layout" only means something with a concrete sample.
Reconsider — what concrete input/output would remove the guesswork here?
"Fix the bug in the checkout flow." (no description of what "fixed" looks like)
Right — how will you know it's actually fixed? That's missing.
Reconsider — this prompt never says what "done" looks like.
"Add input validation." (asked cold, with no existing code pasted in)
Right — validation of what, added to what? There's nothing to anchor to.
Reconsider — what existing material is missing from this prompt?
